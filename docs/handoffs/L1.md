# Übergabe L1 – Konten-Oberfläche der PWA

Branch `l1-auth-ui` (nicht gepusht, kein Remote). Vertrag: `../timetrack-backend/contracts/openapi.yaml` v0.1.0, unverändert.
Code, Tests, Schlüssel englisch; alle sichtbaren Texte deutsch in `src/lib/i18n/de.ts`.

## Routen und genutzte API-Aufrufe

Gruppen: `(public)` leitet angemeldete Nutzer nach `/`; `(app)` ist der Routenwächter (GET `/api/v1/auth/session`
bei jeder Navigation; 401 -> `/login?next=…`; Recovery-Sitzung -> nur `/recover/passkey`; Admin-Seite nur Rolle `admin`).

| Route | Aufrufe |
|---|---|
| `/login` | POST auth/login/options, POST auth/login/verify |
| `/invite/[token]` | GET invitations/{token}, POST auth/register/options, POST auth/register/verify |
| `/setup/recovery` (nach Registrierung) | GET me/recovery + Aufrufe der Wiederherstellungs-Verwaltung (siehe `/settings/recovery`) |
| `/recover` | POST auth/recovery/start, POST auth/recovery/complete |
| `/recover/passkey` (Recovery-Sitzung) | POST me/passkeys/options, POST me/passkeys/verify, GET auth/session, ggf. DELETE auth/session |
| `/` | nur Sitzung |
| `/settings/passkeys` | GET me/passkeys, POST me/passkeys/options+verify, PATCH/DELETE me/passkeys/{id} |
| `/settings/recovery` | GET me/recovery; POST/DELETE recovery-codes; PUT/DELETE fallback-password; PUT/DELETE email; POST email/verify |
| `/settings/sessions` | DELETE me/sessions |
| `/admin/invitations` | GET/POST admin/invitations, DELETE admin/invitations/{id} |
| Layout | DELETE auth/session (Abmelden) |

Client: `src/lib/api/client.ts` (handgeschriebener Fetch-Wrapper, `credentials: 'include'`, `X-CSRF-Token` auf allen
nicht-GET-Aufrufen, Token aus jeder Session-Antwort übernommen, einheitlicher `ApiError{status,code}`).
WebAuthn: `src/lib/webauthn.ts` (parse*FromJSON/toJSON, sonst base64url-Fallback; Fehlerarten unsupported/cancelled/already_registered/failed).
Fehler -> Deutsch: `errorMessage()` in `src/lib/i18n/index.ts` (`error.<code>`, sonst `error.status_<http>`).

## Mock-Modus

`npm run dev:mock` (= `VITE_MOCK=1 vite dev`): Vite-Middleware aus `mock/` bedient `/api` im Speicher (Zustand weg bei Neustart),
und `webauthn.ts` liefert gefälschte Credentials (kein Authenticator nötig). Demodaten: Admin-Konto `admin`,
Einladungstoken `demo-invite`, Recovery-Code `AAAA-BBBB-CCCC`, Rückfallpasswort `correct-horse-battery`, E-Mail-Code `123456`.
Anmeldung im Mock meldet das zuletzt aktive Konto (Admin zu Beginn) an; Signaturen werden nicht geprüft.
Gleiche Mock-Logik (`mock/api.ts`, `mock/fetch.ts`) dient den Vitest-Tests.

## Entwicklung gegen das echte Backend

`npm run dev` proxyt `/api` auf `http://127.0.0.1:18080` (`BACKEND_URL` überschreibbar) - eine Origin, damit der HttpOnly-Cookie
`tt_session` funktioniert. WebAuthn: im Dev-Profil Origin `http://localhost:5173` mit RP-ID `localhost` (also `localhost`, nicht
`127.0.0.1` im Browser öffnen). Produktionsähnlich: Backend liefert `build/` aus (Origin `http://localhost:18080`, RP-ID `localhost`)
und muss für unbekannte Pfade `build/index.html` liefern (SPA-Fallback; `adapter-static` mit `fallback: 'index.html'`).
Kein Node im Produktionsbetrieb.

- Mobile Breite (<500 px) und Dunkelmodus nur im Code berücksichtigt, nicht per Screenshot geprüft (Headless-Fenster hat Mindestbreite).

## Offene Vertragsfragen (Vertrag nicht geändert)

1. Fehlercodes sind nicht aufgezählt. Die UI kennt: `bad_request, unauthorized, forbidden, not_found, conflict, handle_taken,
   last_passkey, too_many_requests, not_implemented, invalid_code, csrf_invalid, recovery_session_restricted, reauth_required`;
   unbekannte Codes fallen auf den HTTP-Status zurück. Bitte endgültige Codeliste festlegen (409 beim Handle-Konflikt, 409 beim letzten Passkey).
2. `POST /me/passkeys/options` verlangt "frische Authentisierung oder Recovery-Sitzung", aber es gibt keinen Re-Auth-Endpunkt und keinen
   dokumentierten Fehler. Die UI zeigt bei `reauth_required` den Hinweis, sich erneut anzuloggen. Gewünscht: Fehlercode/Statuscode und ggf. Re-Auth-Ablauf.
3. Bleibt die Sitzung nach `POST /me/passkeys/verify` in einer Recovery-Sitzung `recovery=true`? Die UI liest die Sitzung neu: wenn
   weiterhin `recovery=true`, meldet sie ab und schickt zur Anmeldung mit dem neuen Passkey; sonst weiter zu `/settings/passkeys`.
4. `register/verify` liefert 400/409, aber `register/options` kennt 409 (Handle vergeben) nicht; fehlt `400` für Validierungsfehler dort?
5. Recovery-Start-Antwort enthält keinen Hinweis, welche Methoden aktiv sind (gewollt, wegen Kontoexistenz); die UI zeigt alle drei Methoden.
6. `GET /me/recovery` liefert `recoveryCodes.remaining` optional; die UI zeigt "Übrige Codes: n", fehlt es, 0.
7. Es gibt keinen Endpunkt zum Auflisten der Sitzungen; `/settings/sessions` bietet nur "Andere Sitzungen abmelden".
8. Ist `DELETE /auth/session` in einer Recovery-Sitzung erlaubt (UI nutzt es zum Abmelden)? Vertrag nennt nur Passkey-Einrichtung und Sitzungswiderruf.
9. `Session.expiresAt` wird nicht ausgewertet (kein automatisches Abmelden vor Ablauf; 401 führt zur Anmeldung).
10. Einladungslink-Format: PWA nimmt `<origin>/invite/<token>`; falls das Backend einen anderen Pfad ausgibt (`bootstrap-admin`), abstimmen.
