## UI-Anpassung
- Zustimmungsseite: Hinweis unter „Anderes Konto verwenden“. Grund (beantwortet L15-Frage 2): Das Backend bindet die Anfrage beim ersten Abruf an Konto UND Sitzung. Nach dem Wechsel (auch zum selben Konto mit neuer Sitzung) liefert dieselbe URL 404 („abgelaufen oder anderes Konto“); die Verbindung muss im Client neu gestartet werden. E2E belegt es.
- L15-Annahme 1 (409 bei entschiedener Anfrage) trifft nicht zu: GET auf eine entschiedene Anfrage liefert 404 (die PWA zeigt dann den „abgelaufen“-Text); POST auf eine entschiedene Anfrage liefert 409.

## Backend (keine Fehler, zwei Abweichungen/Beobachtungen, nichts mit test.fixme)
1. Abweichung vom C16-Handoff („jeder Fehlversuch verbrennt den Code“): Ein falsches `resource` im Token-Request (OAuthService.swift ca. Zeile 216) und eine unbekannte `client_id` werden vor dem Verbrauch des Codes abgewiesen; der Code bleibt danach mit den richtigen Parametern einlösbar. Reproduktion: Code per Flow holen, `POST /oauth/token` mit `resource=https://other.example/mcp` -> 400, derselbe Code mit korrekten Parametern -> 200. Kein Sicherheitsproblem (PKCE-Verifier ist nötig), nur Dokumentation/Test anpassen oder Reihenfolge ändern. Falscher Verifier und falsche `redirect_uri` verbrennen den Code wie beschrieben.
2. Beobachtung: `GET /api/v1/time/timer` liefert das laufende Segment selbst (kein `running`-Feld), ohne Timer `null`.
3. Beobachtung: IDs in Großbuchstaben, Schlüsselreihenfolge in JSON nicht stabil (Tests vergleichen geparst).
